B-

Three of last review's four high-severity defects are fixed; one new high-severity bug in the CubicVol local vol section, and extrapolation still fails silently with NaN

All 665 tests pass in 5.5 s and ruff reports 9 findings (6 of them undefined names in two notebooks). The LV section calibrator and the PDE pricer now start from the same time, interpolation no longer returns NaN on its end nodes, flat local vols no longer inherit an integer dtype, and requires-python matches the syntax in use. The grade moves up from C+ to B- rather than to B for two reasons, both reproduced: (1) CubicVolSection.value passes the raw wing parameters to a formula that expects the derived epsilons, so the CubicVol local vol is not the function it claims to be; (2) a yield curve built on discount or log-discount returns NaN past its last pillar without any error, and the Monte Carlo pricer multiplies that NaN into the PV. Four findings from the 22nd review are still open: the linear matrix LV reload, the FX forward mismatch, the test-fixture default data root, and the broken demos.

Fixed since the 22nd review (4 of 10, verified in the current files): the LV section calibrator starts the first expiry at FWD_PDE_START_TIME, like the pricer (lvsection_calib.py:189, 280)  ·  Interpolation.value only extrapolates strictly outside the grid, so node values are no longer NaN (interpolation.py:298–299)  ·  flat local vols use np.full(np.shape(logm), vol, dtype=float) (localvol.py:271, 332)  ·  requires-python = ">=3.12" (pyproject.toml:13).
Still open from the 22nd review: issues #3, #6, #7 and #10 below, the US federal holiday default calendar on equity payoffs (basic.py:235, 465, exotics.py:15, 74), and part of the annotation list (see Type Safety).

#1 CubicVolSection.value feeds the wing vols vl, vr to a formula that expects the epsilons, so the CubicVol local vol is the wrong function High
sdevpy/volatility/impliedvol/models/cubicvol.py · lines 31, 35–36, 44–47  ·  sdevpy/volatility/localvol/localvol.py · lines 162–164

Why it's bad: The section is built on cubicvoleps_formula, whose last two arguments are epsl and epsr. update_params computes them into self.eff_params, but the override that used them is commented out (lines 35–36), so the base class runs self.formula(self.time, x, self.params) with vl and vr in the epsilon slots. Reproduced with the sample parameters at t = 1 and log-moneyness −0.2, 0, 0.2: section.value gives 0.2776, 0.2500, 0.2378 and cubicvol() gives 0.2760, 0.2500, 0.2390. A CubicVol calibration therefore fits a shape in which vl and vr are cubic coefficients, not the wing levels that cubicvol_check_params validates and the bounds assume. The tests only call cubicvol.cubicvol() directly, so nothing catches it.

Fix: restore the override in CubicVolSection (after line 33), with the base-class signature:

    # def value(self, t, x):
    #     return self.formula(t, x, self.eff_params)
    def value(self, x: npt.ArrayLike) -> npt.ArrayLike:
        """ The formula takes the epsilons, not vl/vr """
        if self.eff_params is None:
            raise ValueError("Invalid CubicVol parameters")
        return self.formula(self.time, x, self.eff_params)

Add a test in test_impliedvol.py, and recalibrate any stored CubicVol local vols:

def test_cubicvol_section_matches_formula():
    section = create_section(1.0)
    x = np.array([-0.2, 0.0, 0.2])
    assert np.allclose(section.value(x), cubicvol.cubicvol(1.0, x, *section.params))

#4 The LV section calibrator never checks whether the optimizer converged Medium
sdevpy/volatility/localvol/lvsection_calib.py · lines 119–133, 152

Why it's bad: After optimizer.minimize or least_squares, the code takes result.x, writes it into the local vol and moves to the next expiry. result.success and result.message are never read. #6 The FX vol stack builds forwards without the spot-date adjustment that FxForwardCurve applies (open since the 22nd review) Medium
sdevpy/volatility/fx/fxvolcalib.py · lines 76–77  ·  sdevpy/volatility/fx/fxvolinterpolation.py · line 241  ·  sdevpy/volatility/fx/fxdeltastrike.py · line 226  ·  sdevpy/calibration/fx/fxforward.py · lines 20, 23

Why it's bad: FxForwardCurve first converts the quoted spot to its t = 0 equivalent, spot0 = spot / df_f(spot_date) * df_d(spot_date), and returns spot0 * df_f(T) / df_d(T). The calibrator, the surface interpolation and strike_from_delta all use spot * df_f(T) / df_d(T). The two differ by the factor df_d(spot_date) / df_f(spot_date), that is the rate differential over the two-day spot lag. The stored 'fwd' in each tenor report defines the moneyness axis of the surface, so a pricer that takes its forward from CalibrationDataSet.get_fxforwardcurve reads every smile slightly off-centre.

Fix: convert the spot once, in FxVolCalibrator._fetch_market_data (after line 234; add fx_spot_date to the fxdates import on line 12), and do the same where FxVolInterpolation receives its spot (fxvolinterpolation.py:357):

        # t = 0 equivalent of the quoted spot, as in FxForwardCurve.load_calibrated
        sdate = fx_spot_date(self.date, self.forccy, self.domccy)
        self.spot = self.spot * self.domcurve.discount(sdate) / self.forcurve.discount(sdate)

Add a test that report['fwd'] equals calib.get_fxforwardcurve(pair, mkt).value(settlement) for each tenor.
