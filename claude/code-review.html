A large restructuring of sdevpy/llms/ — genuine test coverage finally landed, but the moved examples/gpt/raschka/ demo scripts are almost entirely broken, and two new bugs shipped in the rewritten core

This was the biggest single change set reviewed so far: 8 commits reorganizing sdevpy/llms/gpt/, adding a new GptModel wrapper (sdevpy/llms/gpt_model.py), and moving examples/raschka/ to examples/gpt/raschka/. All previously-tracked fixes from the 13th review are confirmed still in place, plus several more landed in this pass: the TorchLearningModel device bug is fixed, KerasLearningModel's constructor kwarg mismatch is fixed, McHestonGenerator's print pollution is fixed, and — the standout improvement — sdevpy/llms/ went from zero test coverage to a genuinely thorough test suite (test_llms.py, 30+ tests) plus a real end-to-end integration test for the GPT stack (test_gpt.py). Two of the library's own known-broken files (modelconverter.py, dead datasets.py) were deleted outright rather than left to rot. However, the examples/gpt/raschka/ directory that everything was moved into has broken imports in the majority of its files — a mix of stale pre-refactor paths and sibling-import issues from the move itself — and the rewritten core introduced two new bugs: multi-turn chat history is silently dropped in GptModel.chat(), and load_model_from_path still never actually moves the loaded model to the target device.

Confirmed fixed since 13th review (verified via direct file reads, not diff stats alone): TorchLearningModel.__init__ now correctly does self.base_model.to(self.device) — GPU training works  ·  KerasLearningModel.load_learning_model now uses set_scalers() instead of invalid constructor kwargs  ·  McHestonGenerator.generate_samples()'s print() calls converted to log.info()  ·  gpt.py::load_model_from_path now takes a proper device parameter with map_location and gracefully handles a missing weight file  ·  the admittedly-broken modelconverter.py (240+ lines, author's own docstring said it didn't work) deleted entirely  ·  dead datasets.py (InstructionDataset, unused anywhere) deleted  ·  sdevpy/llms/ now has 30+ tests across local_model/transformers_model/llama_model/llmfactory, plus a real end-to-end integration test for the GPT stack in test_gpt.py
New in this pass, or still open: GptModel.chat() silently drops all but the last message in a conversation — see #1  ·  load_model_from_path still doesn't move the model to the resolved device — see #2  ·  most of examples/gpt/raschka/ has broken imports post-move — see #3  ·  the nn.Linear(..., GELU()) activation-as-bias bug survived the rename to app_dnn.py — see #4

#1 GptModel.chat() silently drops every message except the last one High
sdevpy/llms/gpt_model.py · lines 41-46

Why it's bad:

prompt = ''
for message in messages:
    new_prompt = message.get("content", "")
    prompt = new_prompt + "\n"
return self.respond_prompt(prompt, **kwargs)

Each loop iteration overwrites prompt instead of accumulating it — after the loop, prompt only ever contains the last message's content. Every earlier message in the conversation, including any system prompt passed through LocalModel.respond_instruction, is silently discarded before the model ever sees it. The method's own comment (line 38-40: "we just write back the answer to the concatenated list of inputs") states the intended behavior — concatenation — which the code doesn't actually do. This is on a live path: llmfactory.run_instruction → LocalModel.respond_instruction → GptModel.chat → this loop.

Fix:

prompt = new_prompt + "\n"
prompt += new_prompt + "\n"
#2 load_model_from_path resolves a device correctly but never actually moves the model there High
sdevpy/llms/gpt/gpt.py · lines 169-188  ·  reachable via sdevpy/llms/gpt_model.py · line 104

Why it's bad: device is correctly resolved and passed to torch.load(weight_file, map_location=device) (line 183), fixing the crash this had in the 13th review. But model = GptModule(model_config) (line 179) constructs the model fresh on CPU, and model.load_state_dict(...) (line 184) only copies parameter values in place — it does not move the model's own tensors to a different device. The function returns model still sitting on CPU regardless of what device resolved to. GptModel.load() calls this with self.device already correctly computed (gpt_model.py:104), so on a GPU machine the returned model is silently left on CPU while later code may pass it CUDA tensors — the same class of device-mismatch bug already found and fixed once this session in TorchLearningModel.__init__.

Fix:

model.load_state_dict(checkpoint["model_state_dict"])
model = model.to(device)
#3 Most of examples/gpt/raschka/ has broken imports after the move from examples/raschka/ High
examples/gpt/raschka/ch3_coding_attention.py, ch4_gpt_model.py, ch5_loadgpt2.py, ch5_pretraining.py, app_dnn.py

Why it's bad: Verified by tracing every import against the actual filesystem. Three distinct broken patterns, several files hitting more than one:

# Pattern A — sdevpy.projects doesn't exist anywhere in the repo
from sdevpy.projects.raschka import raschka_dnn                          # ch4_gpt_model.py:7
from sdevpy.projects.raschka.raschka_gpt_download import ...              # ch5_loadgpt2.py:4

# Pattern B — stale pre-refactor package path
from sdevpy.machinelearning.llms.attention import ...                     # ch3_coding_attention.py:3-4
from sdevpy.machinelearning.llms.gpt import GELU                          # app_dnn.py:3
import sdevpy.machinelearning.llms.textgen as tg                          # ch4_gpt_model.py:8, ch5_loadgpt2.py:6

# Pattern C — sibling files renamed during the move, callers not updated
from raschka.raschka_tokenizers import ...       # ch2_working_with_text.py:5 — now app_tokenizers.py
from raschka.raschka_dummpy_gpt import DummyGPTModel  # ch4_gpt_model.py:5 — now app_dummy_gpt.py

# Bonus — even the "correct-looking" path fails, since __init__.py is empty
from sdevpy.llms.gpt import GptModule             # ch5_pretraining.py:5 — needs .gpt.gpt, not .gpt

Of the files under examples/gpt/raschka/, only app_dummy_gpt.py and app_tokenizers.py have no import issues. Even the sibling-import pattern (from raschka.X import Y) is structurally fragile beyond the wrong filenames: it only resolves if the parent of the raschka package is on sys.path, which isn't the case when running a script directly from inside its own directory.

Fix: Update each import to its current location (sdevpy.llms.gpt.attention, sdevpy.llms.gpt.gpt, sdevpy.llms.gpt.textgen, local files by their new names), and run these scripts end to end at least once to catch what a read-through misses.

#4 nn.Linear(in, out, GELU()) — activation passed as the bias argument, survived the file's rename Medium
examples/gpt/raschka/app_dnn.py · lines 25-29

Why it's bad:

nn.Sequential(nn.Linear(layer_sizes[0], layer_sizes[1], GELU())),
nn.Sequential(nn.Linear(layer_sizes[1], layer_sizes[2], GELU())),
... (5 layers total, same pattern)

nn.Linear's third positional parameter is bias: bool, not an activation module. GELU() is truthy, so it's silently accepted as bias=True and then discarded — no activation is ever applied between layers, and the "deep" network this class is meant to demonstrate (for illustrating vanishing/exploding gradients with shortcut connections) is actually a stack of purely linear transformations. This exact bug was flagged when the file was still named raschka_dnn.py; it carried over unchanged through the rename to app_dnn.py. It's also currently unreachable due to #3's broken GELU import, compounding the two issues.

Fix: nn.Sequential(nn.Linear(layer_sizes[0], layer_sizes[1]), GELU()) — GELU() as a separate item in the Sequential, not an argument to Linear.

def dialog(self, start_text):

#8 GptModel (wrapper) and GptModule (network) — a one-letter naming collision Low
sdevpy/llms/gpt_model.py · line 12  ·  sdevpy/llms/gpt/gpt.py · line 11

Why it's bad: Not a functional bug — traced both classes and confirmed GptModel genuinely just wraps GptModule via gpt.load_model_from_path, no duplicated logic. But the two names differing by a single letter (Model vs. Module) is a real maintainability hazard: searching for "GptModel" won't surface the actual transformer architecture class, and a future contributor skimming either name could easily conflate the two.

Fix: Rename one — e.g. GptModule → GptTransformer or GptModel → GptBackend — to make the distinction unambiguous at a glance.

#9 test_gpt.py's only assertion pins an exact, unseeded-beyond-one-call generated string Low
sdevpy/tests/test_gpt.py · lines 22-29

Why it's bad: The test genuinely exercises the full stack end-to-end (load, train, generate) — a real improvement over having nothing — but its only check is assert response[:15] == "he, was\n,. had.", an exact match against one specific training run's output. This is fragile to PyTorch version differences, CPU/GPU execution differences, or any op-level nondeterminism beyond the single torch.manual_seed(123) call in GptModel.train() — a passing/failing result here says more about bit-for-bit reproducibility than about model correctness.

Fix: Assert on structural properties instead (response is non-empty, correct type, roughly expected length) rather than an exact string, or clearly mark this as a golden/regression test if pinning exact output is intentional.
