#1 scikit-learn is optional in pyproject.toml but still imported at module level by the core calibration stack High
sdevpy/maths/metrics.py · lines 1–16  ·  pyproject.toml · lines 19–23

Verified (unchanged since the 19th review): metrics.py line 3 is still from sklearn.metrics import mean_squared_error, and scikit-learn is listed only under the ml extra. metrics is imported at module level by impliedvol_calib.py:6, optionsurface.py:9 and lvsection_calib.py:14. test_llms.py and test_gpt.py import the torch/transformers stack and there is no importorskip anywhere in sdevpy/tests. (The dev venv has every extra, so I did not run a clean core-only install; the failure follows from the import chain.)

Why it's bad: pip install sdevpy succeeds, but importing the implied-vol and local-vol calibrators raises ModuleNotFoundError: No module named 'sklearn'. The only use is three one-line squared-error formulas that NumPy provides.

Fix — in sdevpy/maths/metrics.py:

from sklearn.metrics import mean_squared_error

def mse(set1, set2):
    return mean_squared_error(set1, set2)
    return float(np.mean((np.asarray(set1) - np.asarray(set2)) ** 2))

def rmsew(set1, set2, weights):
    return np.sqrt(mean_squared_error(set1, set2, sample_weight=weights))
    d2 = (np.asarray(set1) - np.asarray(set2)) ** 2
    return float(np.sqrt(np.average(d2, axis=0, weights=weights).mean()))

def rmse(set1, set2):
    return np.sqrt(mean_squared_error(set1, set2))
    return float(np.sqrt(mse(set1, set2)))

Then add torch = pytest.importorskip("torch") (and transformers) at the top of test_llms.py and test_gpt.py.

#2 Library code changes NumPy's process-wide error state and restores it to a hard-coded value (or not at all) Medium
sdevpy/volatility/impliedvol/models/sabr.py · lines 30–35  ·  sdevpy/volatility/mlsurfacegen/smilegenerator.py · lines 113, 132

Verified by running it: 

np.seterr(invalid='raise')
print(np.geterr()['invalid'])                 # raise
sabr.sabr_from_dict(1.0, k, 0.025, params)
print(np.geterr()['invalid'])                 # warn  -- the caller's setting was silently overwritten

Why it's bad: sabr.implied_vol calls np.seterr(invalid='ignore') and later np.seterr(invalid='warn') instead of restoring the previous value, so any caller (or test) that had chosen 'raise' loses it after the first SABR call. If the np.where between the two calls raises, invalid stays 'ignore' for the rest of the process, hiding genuine NaNs everywhere. SmileGenerator.to_nvol does the same with divide='raise'/'warn' without try/finally. (SabrGenerator.generate_samples_inverse does it correctly with old = np.seterr(...) and finally.)

Fix — use the context manager, which restores the previous state on exit, even on exceptions. In sabr.py:

np.seterr(invalid='ignore')
z2 = z * z
correction = np.where(z2 > 10.0 * m_epsilon, ..., ...)
np.seterr(invalid='warn')
z2 = z * z
with np.errstate(invalid='ignore'):
    correction = np.where(z2 > 10.0 * m_epsilon,
                          z / np.log((np.sqrt(1.0 - 2.0 * rho * z + z2) + z - rho) / (1.0 - rho)),
                          1.0 - 0.5 * rho * z - (3.0 * rho * rho - 2.0) * z2 / 12.0)

and in smilegenerator.py to_nvol, wrap the loop instead of the two np.seterr lines:

np.seterr(divide='raise')
...loop...
np.seterr(divide='warn')
with np.errstate(divide='raise'):
    for i in range(num_samples):
        ...
#3 Noise injection in the SABR generator uses the global NumPy RNG, so seeded datasets are not reproducible Medium
sdevpy/volatility/mlsurfacegen/sabrgenerator.py · lines 233, 237  ·  smilegenerator.py · line 24

Verified by reading (not executed): SmileGenerator.__init__ creates self.rng = np.random.RandomState(seed) (default seed 42) and generate_samples draws all parameters from it. But in price_straddles_ref, the optional noise uses np.random.rand() twice per strike (line 233 decides whether to add noise, line 237 draws its size).

Why it's bad: With noise_prob > 0 two generators built with the same seed produce different training sets, so a model result cannot be reproduced or compared across code changes, and a failing test cannot be replayed. The global RNG is also shared with anything else in the process.

Fix — in sabrgenerator.py, draw from the generator's own RNG:

rand = np.random.rand()
rand = self.rng.rand()
use_noise = (rand < noise_prob)
if use_noise:
    noise = (np.random.rand() - 0.5) * rel_noise / 0.5
    noise = (self.rng.rand() - 0.5) * rel_noise / 0.5

Add a test that two SabrGenerator(seed=1) instances with noise_prob=0.5 return identical output.

#9 .claude/settings.json: the new deny rules are sound, but the bare Bash allow can still write Python files and some cruft remains Low
.claude/settings.json · lines 3–15 (deny), 16–37 (allow), 38–41 (additionalDirectories)

Verified by reading the current file (read first, as before): the deny block now blocks Edit/Write/NotebookEdit on *.py and *.ipynb and sed -i, git checkout, git clean; the allow list dropped ~35 redundant entries. Remaining points:

Why it's bad: (a) The bare "Bash" allow still permits shell redirection (cat > x.py, tee) and interpreter writes (python -c "open('x.py','w')..."), which the deny prefix rules do not match, so the read-only rule is still partly convention. (b) Four PowerShell(...) entries and "\\tmp" in additionalDirectories are Windows leftovers on a macOS machine. (c) Bash(git checkout*) also blocks the everyday git checkout <branch>; if that is unintended, git restore-style commands are the ones worth blocking.

Fix — for (a), a PreToolUse hook on Bash is the reliable barrier:

// .claude/settings.json
"hooks": {
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{ "type": "command",
      "command": "python3 -c \"import json,sys,re; c=json.load(sys.stdin)['tool_input']['command']; sys.exit(2 if re.search(r'(>|tee |open\\()[^|;&]*\\.(py|ipynb)\\b', c) else 0)\"" }]
  }]
}
// and delete: the four "PowerShell(...)" entries and "\\tmp" from additionalDirectories

Exit code 2 from a hook blocks the call and returns the message to Claude. This is a heuristic filter, not a sandbox; test it on a throwaway file first.

#10 calibrate_batch logs a failed calibration without its traceback and returns None for it Low
sdevpy/volatility/fx/fx_calib_batch.py · lines 44–49

Verified: the handler is except Exception as exc: log.error(f"Calibration failed for {pair} on {date}: {exc}"), then results[(pair, date)] = None.

Why it's bad: For a batch of pairs and dates run in worker processes, "Calibration failed: 'tenor'" with no traceback rarely says which line failed. The None entries also flow to callers that must remember to check for them (the __main__ block indexes all_results[...] and immediately uses the report).

Fix — keep the batch running but keep the evidence:

            except Exception:
                log.error(f"Calibration failed for {pair} on {date}: {exc}")
                log.exception(f"Calibration failed for {pair} on {date}")
                results[(pair, date)] = None

# and at the end of calibrate_batch:
n_failed = sum(1 for r in results.values() if r is None)
if n_failed:
    log.warning(f"{n_failed} of {len(results)} calibrations failed, see errors above")
