#1 scikit-learn was moved to an optional extra, but core calibration code still imports it through sdevpy.maths.metrics High
sdevpy/maths/metrics.py · line 3  ·  pyproject.toml · lines 19–23

Verified: read the current files. pyproject.toml now lists scikit-learn only under [project.optional-dependencies] ml, yet metrics.py starts with from sklearn.metrics import mean_squared_error. metrics is imported at module level by volatility/impliedvol/impliedvol_calib.py:6, volatility/impliedvol/optionsurface.py:9 and volatility/localvol/lvsection_calib.py:14 — the non-ML implied-vol and local-vol calibration stack. (This environment has every extra installed, so I could not run a clean core-only install; the failure follows directly from the import chain.)

Why it's bad: pip install sdevpy now succeeds, but importing the calibrators raises ModuleNotFoundError: No module named 'sklearn'. The sole use is three one-line squared-error formulas that NumPy does natively, so a 30 MB dependency is being demanded for arithmetic. Likewise test_llms.py and test_gpt.py import the torch/transformers stack unconditionally, so a core-only pytest fails at collection.

Fix — in sdevpy/maths/metrics.py, drop the sklearn import and use NumPy (equivalent to sklearn's uniform-average behaviour for 1-D and 2-D inputs):

from sklearn.metrics import mean_squared_error

def mse(set1, set2):
    return mean_squared_error(set1, set2)
    return float(np.mean((np.asarray(set1) - np.asarray(set2)) ** 2))

def rmsew(set1, set2, weights):
    return np.sqrt(mean_squared_error(set1, set2, sample_weight=weights))
    d2 = (np.asarray(set1) - np.asarray(set2)) ** 2
    return float(np.sqrt(np.average(d2, axis=0, weights=weights).mean()))

def rmse(set1, set2):
    return np.sqrt(mean_squared_error(set1, set2))
    return float(np.sqrt(mse(set1, set2)))

Then add pytest.importorskip("torch") / importorskip("transformers") at the top of test_llms.py and test_gpt.py, and add a CI job that installs only the core dependencies and runs pytest, so this class of regression is caught automatically.

#2 implied_vol_brent returns confident wrong values: 1e-6 for a deep-OTM 30% option, 3265% for an infeasible price High
sdevpy/analytics/black.py · lines 42–58 (fallback use at line 115)  ·  sdevpy/volatility/impliedvol/impliedvol.py · line 176

Verified by running it in the project venv: 

black.implied_vol_brent(1.0, 100.0, True, 100.0, 150.0)          # call price 150 > forward 100: infeasible
-> 32.65                                                        # 3265% vol, no error, no NaN
black.implied_vol_brent(0.1, 200.0, True, 100.0, price(0.1,200,True,100,0.30))
-> 1.0e-06                                                      # true answer is 0.30
black.implied_vol_newton(0.1, [200.0, 100.0], True, 100.0, ...)
-> [1.0e-06, 0.30]                                              # Newton's low-vega fallback returns the same wrong value

Why it's bad: The function minimises (price(vol) - target)**2 with Brent's minimiser on a two-point bracket. Squared error is tiny (<1e-16) everywhere for low-vega options, so the tolerance test stops immediately at the bracket edge; and for infeasible prices the minimiser follows the downhill direction outside the bracket instead of failing. The Newton implementation hands exactly its hardest strikes (vega < 1e-6) to this function, so the "robust fallback" is the least reliable path. It is also the inverter used by ParametricImpliedVol.black_volatility whenever the model is not log-normal-quoted, so wings of calibrated surfaces silently get vols of ~0 or absurd size.

Fix — replace the minimiser with a bracketed root-finder on the price difference, and reject infeasible targets explicitly:

from scipy.optimize import brentq

def implied_vol_brent(expiry, strike, is_call, fwd, fwd_price):
    options = {'xtol': 1e-6, 'maxiter': 100, 'disp': False}
    ...
    res = minimize_scalar(fun=error, bracket=(xmin, xmax), options=options, method='brent')
    return res.x
    w = 1.0 if is_call else -1.0
    intrinsic = max(w * (fwd - strike), 0.0)
    upper = fwd if is_call else strike            # no-arbitrage upper bound
    if not (intrinsic < fwd_price < upper):
        raise ValueError(f"Price {fwd_price} outside no-arbitrage bounds ({intrinsic}, {upper})")

    f = lambda vol: price(expiry, strike, is_call, fwd, vol) - fwd_price
    return brentq(f, 1e-8, 10.0, xtol=1e-12, rtol=1e-12)

Add two tests to test_analytics.py: a round-trip (price → implied_vol_brent) on a deep-OTM strike (e.g. the case above, expecting 0.30 ± 1e-8), and pytest.raises(ValueError) for the infeasible price. Callers that vectorise (implied_vols_brent, implied_vol_newton) should decide whether to catch the error and emit NaN.

#3 Variance keeps a stale current_fixing when the same payoff is re-valued on another date Medium
sdevpy/montecarlo/payoffs/basic.py · lines 507–528 (set_valuation_date), 474–481 (evaluate)

Verified by running it: after set_valuation_date(2025-12-15) the payoff holds current_fixing = 96.6814. Calling set_valuation_date(2025-11-15) on the same object (valdate = swap start, so there are no historical fixings) resets current_sum to 0.0 but leaves current_fixing = 96.6814.

Why it's bad: set_valuation_date only assigns current_fixing inside an if; it never resets it. evaluate() then adds log(spot_0 / 96.68)**2 as if a real fixing existed the day before the swap starts, inflating the variance of every path. Book objects are routinely revalued across dates (scenarios, theta, risk bumps), and the result is a plausible-looking wrong price rather than an error.

def set_valuation_date(self, valdate, md: MarketDataProvider):
    self.eventdates = []
    hist_fixing_dates = []
    self.current_sum = 0.0
    self.current_fixing = None            # do not leak state from a previous valuation date
    ...
    self.current_sum = 0.0               # (the later duplicate assignment can go)
    if hist_fixings is not None and len(hist_fixings) > 1: ...

Add a test that values the same Variance at two dates and compares against a fresh object for each date.

#6 The worst-of barrier trade in test_mc.py cannot distinguish knocked from un-knocked Medium
sdevpy/tests/test_mc.py · lines 45–47, 62  ·  sdevpy/montecarlo/payoffs/exotics.py · lines 26–44

Verified: the test spots are ABC = 100 and XYZ = 50 (from tests/data/marketdata/spot) and the trade is WorstOfBarrier(['ABC','XYZ'], expiry, 90.0, 'Call', 35.0). The worst-of level is ~50, the strike is 90, and the golden value is 0.00330715322. A path only pays if the worst asset finishes above 90, which essentially never happens on a path that also dipped below 35.

Why it's bad: The knock-out branch (payoff[knocked] = 0, and the monitored-date indexing that was the subject of an earlier fix) can be deleted or broken without changing this reference value beyond noise. The test protects against nothing on the barrier logic.

Fix — add a dedicated test whose payoff is materially in the money, so that knocking changes the answer:

def test_worstof_barrier_knocks():
    # Strike 30 vs worst-of level ~50: deep ITM, so the barrier at 45 (near XYZ's spot of 50) matters
    no_barrier = price_worstof(strike=30.0, barrier=0.0)     # never knocks
    with_barrier = price_worstof(strike=30.0, barrier=45.0)  # knocks on many paths
    assert with_barrier < 0.7 * no_barrier
    assert price_worstof(strike=30.0, barrier=1e9) == 0.0    # always knocked

where price_worstof builds a one-trade book like the existing test does.

#9 .claude/settings.json: the "never modify Python files" rule is not enforced by any permission, and the allow-list is bloated Medium
.claude/settings.json · lines 3–70 (allow), 62–66 (deny)

Verified: I read the file before starting, as requested. Findings from the current copy:

Why it's bad: (a) The bare "Bash" entry (line 5) already allows every shell command, which makes the ~30 more specific Bash(...) entries redundant, including one-off leftovers such as Bash(rm -f /tmp/dump_nb.py /tmp/dump_nb2.py), ten dump_nb.py invocations and an awk line with a hard-coded temp file. (b) CLAUDE.md says Python and notebook files must never be edited, but nothing in deny backs that up: Bash(sed*), Bash(cat > *) and the bare Bash can all rewrite a .py file with no prompt. The only protection is the model following instructions. (c) deny covers just three patterns; git checkout -- ., git clean -fd, rm -r -f (flag order) and git commit/git branch -D are not covered. (d) Cruft: Read(//tmp/**) appears twice, four PowerShell(...) entries on a macOS machine, "\\tmp" (a Windows-style path) in additionalDirectories, and Bash(python3 -m pytest sdevpy/tests/test_mc.py -x -q) hard-codes a single test file.

Fix — keep the no-prompt behaviour, but let deny enforce the read-only rule (deny always beats allow, and adds no prompts): 

"deny": [
  "Bash(rm -rf*)", "Bash(git push*)", "Bash(git reset --hard*)",
  "Edit(**/*.py)", "Write(**/*.py)", "Edit(**/*.ipynb)", "Write(**/*.ipynb)", "NotebookEdit(**)",
  "Bash(sed -i*)", "Bash(git checkout*)", "Bash(git clean*)"
],
"allow": [
  "Bash",                                   // keep the bare entry ...
  "Bash(grep*)", "Bash(awk*)", "Bash(wc*)", ... (all redundant)   // ... and delete these
  "Bash(rm -f /tmp/dump_nb.py /tmp/dump_nb2.py)", "Bash(python3 /tmp/dump_nb.py ...)"
  "PowerShell(...)", duplicate "Read(//tmp/**)"
]

Note that prefix-matched Bash rules can be bypassed (cat > x.py, tee, python -c "open(...).write"). For a hard guarantee, add a PreToolUse hook on Bash that rejects commands writing to *.py/*.ipynb.
