#1 get_localvol_or_new's fallback-to-a-fresh-model path is unreachable — it raises instead, for exactly the case it exists to handle High
sdevpy/calibration/provider.py · lines 24-28, 50-56  ·  sdevpy/volatility/localvol/localvol_factory.py · lines 50-53

Why it's bad: The 15th review praised this exact function as the "good graceful-fallback pattern" local vol has that implied vol lacked. Re-reading it this pass shows that praise was misplaced:

# provider.py — no None-check before calling the factory
def get_localvol(name, date, model_name, cal_prov, t_grid=None):
    data = cal_prov.get_localvol_data(name, date, model_name)
    return lvf.get_localvol_from_data(data, t_grid)

# localvol_factory.py — raises instead of returning None
def get_localvol_from_data(data, new_t_grid=None):
    if data is None:
        raise ValueError('LocalVol data is None')

# provider.py — get_localvol_or_new's None-check can never fire
lv = None
if not force_new:
    lv = get_localvol(name, date, model_name, cal_prov, t_grid=t_grid) # raises before returning
if lv is None: # dead branch
    log.info(f"Initializing new LV for {name}")
    lv = lvf.get_localvol_new(t_grid, model_name)

When no calibration file exists yet — the exact scenario get_localvol_or_new is meant to handle — get_localvol_from_data raises before get_localvol can return None, so the if lv is None: branch that creates a fresh model is unreachable through this path. get_localvol_or_new is called from lvsection_calib.py:52 (first-time calibration of a new name) and from provider.py:69 (get_local_vols, used by the Monte-Carlo pricer when no explicit lv_map is supplied) — both realistic, non-exotic call paths. Calibrating or pricing any name with no stored local-vol file crashes with ValueError('LocalVol data is None') instead of initializing the intended fresh model.

Fix: Catch the None-data case before it reaches the raising factory call, e.g. check cal_prov.get_localvol_data(...) is None directly in get_localvol_or_new rather than going through get_localvol, or have get_localvol_from_data accept a raise_on_missing: bool=True flag that the fallback path sets to False.

#2 WorstOfBarrier's barrier monitoring silently depends on which other trades share its pricing book High
sdevpy/montecarlo/payoffs/exotics.py · lines 19-45  ·  sdevpy/montecarlo/payoffs/basic.py · lines 21-29 (list_instrument_eventdates)

Why it's bad: set_valuation_date registers only the expiry as this trade's own event date:

def set_valuation_date(self, valdate, md):
    if self.expiry < valdate:
        raise ValueError("Past trade found")
    self.eventdates = [self.expiry] # no interim monitoring dates registered

But evaluate() monitors the barrier over the entire simulated time axis of mkt_state.event_paths:

paths = mkt_state.event_paths # the whole BOOK's merged event-date grid, not this trade's own
spot_all = self.paths_for_all(paths)
min_path = spot_all.min(axis=2)
knocked = (min_path < self.barrier).any(axis=1) # checked at every date in that merged grid

event_paths's time axis is built from list_instrument_eventdates, which unions the event dates of every instrument in the book, not just this one. Concretely: pricing this trade alone in a book monitors the barrier at essentially one time point (the expiry); adding an unrelated Asian option with a dense daily fixing schedule to the same book adds all of those extra dates to the shared grid, and this trade's knock-in/out result changes purely because of another trade's presence — with no error, and no indication in the API that this dependency exists. The class docstring ("Will need implementation of barrier monitoring first") acknowledges the feature is incomplete, but nothing stops it from being priced today.

Fix: Register the trade's own intended monitoring dates (e.g. daily/weekly grid from trade start to expiry) in set_valuation_date, and index into spot_all using this trade's own date indices rather than assuming every date in the merged grid belongs to it — mirroring how Average/Variance in the same file resolve their own event indices.

#3 FX cross-settlement silently skips the USD calendar for six low-lag currency pairs, contradicting the function's own docstring High
sdevpy/market/fxforward.py · lines 63-98

Why it's bad: The docstring is explicit that crosses always need the USD calendar:

def fx_spot_date(valdate, forccy, domccy):
    """ ... Crosses (neither leg USD) only need the first hop good in the pair's own
        centers, then require USD too, since crosses settle via two USD legs. """
    lag = fx_spot_lag(forccy, domccy)
    pair_cal = make_calendar(f"{forccy},{domccy}")
    if 'USD' in (forccy, domccy):
        return pair_cal.add_business_days(valdate, lag)

    settle_cal = make_calendar(f"{forccy},{domccy},USD") # built...
    date = pair_cal.add_business_days(valdate, 1)
    return settle_cal.add_business_days(date, lag - 1) if lag > 1 else date # ...but never used when lag == 1

FX_SPOT_LAG_OVERRIDES sets lag = 1 for six cross pairs with no USD leg (CAD/KZT, CAD/PHP, CAD/TRY, KZT/PHP, KZT/TRY, PHP/TRY). For exactly these pairs, settle_cal (which includes USD) is constructed and then discarded — the lag > 1 ternary falls through to plain date, validated only against the two-currency pair_cal. If that one settlement day happens to be a US holiday but a good business day for both actual currencies, the function returns a date that isn't actually a valid USD settlement day, directly contradicting its own stated convention. test_fxdata.py's TestFxSpotDate only covers EUR/GBP (default 2-day lag) and USD/CAD (direct USD pair) — no test exercises any of the six affected lag=1 cross pairs.

Fix: Always route the settlement through settle_cal, even for the first hop when lag == 1: return settle_cal.add_business_days(pair_cal.add_business_days(valdate, 1), max(lag - 1, 0)), dropping the special-cased early return.

#6 Golden-master test reference values are rebased in place across six test files, with the old value left commented out beside the new one Medium
sdevpy/tests/test_pde.py · lines 60-61, 81-82  ·  sdevpy/tests/test_mc.py · lines 62-63  ·  also test_localvol_calib.py, test_impliedvol.py, test_localvol.py, test_marketdata.py

Why it's bad: The same pattern recurs across the test suite's numerical core:

pde_ref = np.asarray([2.70428011, 10.60023123, ...])
# pde_ref = np.asarray([2.70606853, 10.6012976, ...])  # old value, left as a comment

In test_pde.py specifically, I traced the two instances against the file's own independent closed-form reference (cf_ref, invariant across both tests): the new pde_ref values are actually closer to cf_ref than the commented-out old ones (e.g. line 60's new value differs from cf_ref[0] by ~0.0006 vs. the old value's ~0.0024) — consistent with a genuine numerical-accuracy improvement, not a regression being papered over. But test_mc.py:62-63 has no such independent cross-check available in the test itself, so there's no way to tell from the test alone whether that rebase reflects a fix or a regression — and neither file documents which it was. Left unexplained, this pattern (confirmed present in at least six files across PDE, Monte Carlo, local-vol and implied-vol calibration tests) weakens confidence that these tests would flag a real future regression, since "matches the last observed output" and "matches the true answer" become indistinguishable in the diff.

Fix: When a reference value changes, delete the old one (git history preserves it) and add a one-line comment stating why it changed (e.g. "updated after fixing #N — bug caused Y% error vs. closed-form"), so a future reader isn't left guessing whether a rebase was a fix or a regression.

#8 Near-identical generate_samples body duplicated across three sibling ML surface generators Medium
sdevpy/volatility/mlsurfacegen/sabrgenerator.py · lines 22-98  ·  mczabrgenerator.py · lines 23-102  ·  mchestongenerator.py · lines 22-101

Why it's bad: All three files carry their own ~75-80 line generate_samples implementation with the same structure — draw parameters, loop over surfaces, percentile-based strike construction via (fwd + shift) * np.exp(-0.5*stdev**2 + stdev*norm.ppf(percentiles)) - shift, flatten to a DataFrame — differing only in which parameters are drawn. Any bug fix or improvement to the shared strike-sampling logic (e.g. the percentile method itself) has to be replicated by hand in three places; a fix applied to one and missed in the others would silently produce inconsistent training data across model families.

Fix: Extract the shared skeleton (strike sampling, DataFrame flattening) into smilegenerator.py as a template method, with each generator supplying only its own parameter-drawing step.

#10 vsvi.py raises "Negative variance" for a quantity its own module docstring says is vol, not variance Low
sdevpy/volatility/impliedvol/models/vsvi.py · lines 1-8, 81-83

Why it's bad:

""" VSVI stands for 'Vol SVI'. ... This model simply gives an SVI-like
    parametric shape to the volatility, as opposed to the variance in the original paper ... """
...
vol = vstar + b * (rho * xm + eta - lambda_)

The module's own header explicitly contrasts VSVI (acts on vol) against original SVI (acts on variance) — the whole point of the model.
