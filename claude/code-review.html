#1 The currently-open training notebook trains on the full dataset, not the training split — test-set RMSE is data-leaked Critical
notebooks/stovol/StoVol Training.torch.ipynb · cell 5 (split) vs. cell 10 (train call)

Why it's bad: The dataset is correctly split: 

# cell 5
x_train, y_train, x_test, y_test = datasets.prepare_sets(x_set, y_set, train_percent)

but training uses the full, unsplit set instead of the training split:

# cell 10
model.set_sample_testing(epoch_sampling, x_test, y_test)
model.train(x_set, y_set, epochs, batch_size, shuffle=True)

Since x_test/y_test are subsets of x_set/y_set, the model is trained on every row it is later "tested" against in cell 12 (test_pred = model.predict(x_test)). The reported test RMSE is therefore not a held-out generalization metric at all — it's measuring memorized training data, exactly the failure mode the split exists to catch. The sibling TensorFlow notebook StoVol Training.ipynb calls model.train(x_train, y_train, ...) correctly, confirming this is a deviation, not the intended pattern.

Fix:

model.train(x_set, y_set, epochs, batch_size, shuffle=True)
model.train(x_train, y_train, epochs, batch_size, shuffle=True)
#2 KerasLearningModel cannot be instantiated — its required abstract method was never implemented Critical
sdevpy/machinelearning/keras/learningmodel.py · lines 12-43  ·  sdevpy/machinelearning/learningmodel.py · lines 61-64

Why it's bad: The base class declares predict_on_scaled as @abstractmethod. KerasLearningModel only defines the concrete method predict (line 38) — predict_on_scaled is never implemented anywhere in its MRO. Python refuses to construct any class with an unimplemented abstract method, so KerasLearningModel(...) raises TypeError: Can't instantiate abstract class KerasLearningModel without an implementation for abstract method 'predict_on_scaled' on every call — including both branches inside load_learning_model (lines 130 and 132). The Keras backend of this wrapper library is entirely non-functional as written. A second, independent bug in the same call is masked by this one: load_learning_model line 130 passes is_scaled=True, x_scaler=x_scaler, y_scaler=y_scaler, but __init__(self, base_model) (line 14) only accepts base_model — those kwargs were commented out and never restored.

Fix: Implement predict_on_scaled (the existing predict already does scaling — split out the scaled-only portion), and restore the constructor's is_scaled/x_scaler/y_scaler parameters to match the call site.

#3 sdevpy/llms/gpt/ — three files import from a package path that no longer exists Critical
sdevpy/llms/gpt/gpt.py · line 10  ·  chat.py · lines 3-4  ·  training.py · line 5

Why it's bad: All three do a top-level import from sdevpy.machinelearning.llms or sdevpy.machinelearning.gpt — neither exists; the real package is sdevpy.llms.gpt:

# gpt.py:10
from sdevpy.machinelearning.llms.attention import MultiHeadAttention

# chat.py:3-4
from sdevpy.machinelearning.gpt import GPTModel
import sdevpy.machinelearning.llms.textgen as tg

# training.py:5
import sdevpy.machinelearning.llms.textgen as tg

Every one of these raises ModuleNotFoundError immediately on import — this looks like a leftover from moving the package from machinelearning/llms to llms/gpt. Beyond the import path, chat.py calls tg.text_to_token_ids, tg.generate_text_simple, and tg.token_ids_to_text — none of which exist in textgen.py (the real names are text_to_tokens, generate, tokens_to_text). And chat.py has no if __name__ == "__main__": guard at all: model loading from a hardcoded C:\temp\llms\model-save.pth and text generation run at module import time, not on demand. No test in sdevpy/tests/ imports anything from llms/gpt/, which is why none of this was caught.

Fix: Update the three import paths to sdevpy.llms.gpt.*, rename the chat.py/training.py calls to match textgen.py's actual function names, and wrap chat.py's executable body in if __name__ == "__main__":.

#4 tssvi2 is excluded from the packaged distribution but imported at module level by the factory that builds it High
pyproject.toml · line 32  ·  sdevpy/volatility/impliedvol/impliedvol_factory.py · line 3

Why it's bad: pyproject.toml excludes the module from the built package:

exclude = ["sdevpy/volatility/impliedvol/models/tssvi2*"]

but impliedvol_factory.py does a top-level, unconditional import of it:

from sdevpy.volatility.impliedvol.models.tssvi2 import TsSvi2

This works fine when running from the source checkout (which is why it hasn't been noticed), but in any pip install-built distribution, tssvi2.py is absent while impliedvol_factory.py ships normally — so importing impliedvol_factory itself fails with ModuleNotFoundError for anyone using the installed package, breaking every model the factory builds (SVI, LogMix, TsSvi1), not just TsSvi2.

Fix: Either remove the tssvi2* exclusion from pyproject.toml (if the model is meant to be public), or make the import lazy/local inside the one function that needs it so the rest of the factory still works without it.

#5 EqVolSurfaceData's size-consistency check can never fail High
sdevpy/market/eqvolsurface.py · lines 24-31

Why it's bad:

self.input_strikes = [np.asarray(s['strikes']) for s in sections]
self.vols = [np.asarray(s['vols']) for s in sections]

n_times = len(self.expiries)
if any(len(x) != n_times for x in (self.input_strikes, self.vols)):
    raise ValueError("Incompatible size along time direction...")

self.input_strikes and self.vols are list comprehensions with exactly one entry per section by construction — so len(self.input_strikes) == len(self.vols) == n_times is always true, regardless of whether an individual section's strikes/vols arrays are mismatched in length or malformed. The check tests the wrong object (the outer list) instead of each inner array, so it can never raise — malformed market data for a single expiry passes through silently.

Fix: Check each section's own arrays, e.g. validate len(s['strikes']) == len(s['vols']) per section during the list-comprehension pass, and check len(self.expiries) == len(sections) for the outer dimension.

#6 Custom extrapolation eps is silently dropped — extrapolators always fall back to the tiny default and can return NaN High
sdevpy/maths/interpolation.py · lines 21-33 (drop point)  ·  lines 201-220 (FlatExtrapolator)

Why it's bad: create_extrapolator doesn't accept or forward **kwargs:

def create_extrapolator(interpolator, type: str='builtin'):
    match type.lower():
        case 'flat': return FlatExtrapolator()  # no kwargs passed through

but FlatExtrapolator.__init__(self, **kwargs) does accept a custom eps (self.eps = kwargs.get('eps', constants.EPS) via its base class) — it just never receives it, since create_extrapolator constructs it with no arguments at all. Any caller who passes create_interpolation(..., eps=0.5) silently gets the library default (constants.EPS = 1e-11) instead. Reproduced directly: with a custom eps=0.5, evaluating a point 0.3 outside the grid returns NaN instead of the intended flat-extrapolated value, because the boundary check in FlatExtrapolator.value() uses the wrong (much smaller) tolerance.

Fix: Change create_extrapolator to accept and forward **kwargs: return FlatExtrapolator(**kwargs), etc.

#7 calculate_with_greeks returns a base value from row 0 only, misaligned with full-batch gradients High
sdevpy/machinelearning/keras/learningmodel.py · lines 94-96

Why it's bad:

base = md_y[0].numpy()          # only the first row of the batch
grads = t.gradient(md_y, md_x_tensor)
diffs = grads.numpy()          # covers the entire batch
return base, diffs

For any x_test with more than one row, base corresponds to sample 0 while diffs covers every sample in the batch — the two returned quantities describe different inputs. Any caller combining base value and Greeks for a batch of more than one point (the normal use case for a vectorized risk calculation) gets a base value that is silently wrong for every row except the first.

Fix: base = md_y.numpy() (drop the [0] indexing) so it covers the same batch as diffs.

#8 Zero test coverage for machinelearning/{pytorch,keras,tensorflow} and llms/gpt — and the coverage config actively hides the gap High
sdevpy/tests/ · (no matches for "pytorch"/"keras"/"tensorflow"/llms.gpt anywhere)  ·  pyproject.toml · lines 57-59

Why it's bad: No file under sdevpy/tests/ imports anything from sdevpy.machinelearning.pytorch, sdevpy.machinelearning.keras, sdevpy.tensorflow, or sdevpy.llms.gpt — confirmed by searching every test file for each package name. This is precisely why issues #2, #3, #6 (in keras/learningmodel.py) and the still-open activation/print issues in pytorch/topology.py have gone unnoticed for multiple reviews. Worse, pyproject.toml's coverage config actively excludes these same directories from measurement: 

[tool.coverage.run]
omit = [
    ...
    "sdevpy/tensorflow/*",
    "sdevpy/machinelearning/*",
    "sdevpy/llms/*"
]

so a coverage report never shows these as gaps at all — the metric that would normally surface "we have 0% coverage here" is configured to stay silent about it instead.

Fix: At minimum, add a smoke test per subpackage (construct a model, run one forward/backward pass, save/load round-trip) to catch import- and instantiation-level breakage like #2 and #3. Separately, remove machinelearning/* and llms/* from the coverage omit list once tests exist, so future gaps are visible in reports rather than hidden by config.

#9 WorstOfBarrier only evaluates the barrier at expiry, not through time — self-documented as unfinished but exported without a runtime guard Medium
sdevpy/montecarlo/payoffs/exotics.py · lines 8-9 (docstring), 19-36 (evaluate), 41-45 (set_valuation_date)

Why it's bad: The class docstring is candid about the limitation — "Not doing by algebra yet. Will need implementation of barrier monitoring first." But nothing stops a caller from constructing and pricing it anyway: set_valuation_date sets self.eventdates = [self.expiry] — the only event date ever registered — so evaluate()'s knocked = (min_path < self.barrier).any(axis=1) (which reads as if it monitors the barrier across multiple time points) degenerates to a single check at expiry. This silently prices a continuously-monitored barrier as if it were a European condition at expiry only — for any barrier level the underlying could have breached and recovered from before expiry, this overstates the surviving payoff. sdevpy/tests/test_mc.py:38 sets the barrier far out of range, so no test would ever exercise (or catch) the missing monitoring.

Fix: Either implement genuine path-wise barrier monitoring (register all monitoring dates as event dates, not just expiry), or — matching how the equivalent WIP-stub issue was resolved in the 9th/10th review cycle — don't export the class from the public payoffs namespace until it's real, so a caller can't accidentally price a fake barrier.

#10 get_pde_config's docstring and t parameter describe an iv_surface-based feature that doesn't exist in the function Medium
sdevpy/pde/forwardpde.py · lines 163-177

Why it's bad:

def get_pde_config(t: float=None, **kwargs) -> PdeConfig:

The function body never references t, and iv_surface does not appear anywhere in forwardpde.py (confirmed by search).
