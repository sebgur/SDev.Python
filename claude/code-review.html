#1 The LV section calibrator runs the first expiry's PDE from t = 0, while the pricer runs it from t = 1/365, so calibration and repricing disagree High
sdevpy/volatility/localvol/lvsection_calib.py · lines 194, 284–286, 301

What happens: LvObjectiveBuilder.__init__ sets self.start_time = 0.0 (line 194). The calibration loop calls set_expiry(0, …) first, and that builds the step grid from self.start_time: 

ts = self.start_time if self.exp_idx == 0 else self.expiry_grid[self.exp_idx - 1]   # line 284 → ts = 0.0
self.step_grid = timegrids.build_timegrid(ts, te, self.pde_config)                     # line 286: linspace(0, T1)

Only later, on the first objective call, does initialize() set self.start_time = fpde.FWD_PDE_START_TIME (line 301). By then the grid already exists. The mollifier density it builds already represents time 1/365, and slice 0 then diffuses it for another full [0, T1], which is one extra day of variance. forwardpde.calculate_densities (used by price_vanilla_surface) correctly starts at FWD_PDE_START_TIME.

Why it's bad: The optimiser fits parameters to a density that has 1/365 too much variance. When the calibrated LV is repriced with the library's own PDE, the result does not match the calibration targets. Under a flat 20% LV, the first-expiry vol comes out as 0.20·√(31/30) ≈ 20.33% at 30 days, an error of about 33 bp that sits entirely in the section every later expiry builds on.

Fix: initialise the start time before any grid is built, and drop the late assignment:

# lvsection_calib.py, __init__ (line 194)
-        self.start_time = 0.0
+        self.start_time = fpde.FWD_PDE_START_TIME  # must match forwardpde.calculate_densities

# lvsection_calib.py, initialize() (line 301)
-        self.start_time = fpde.FWD_PDE_START_TIME

Then add a test in test_localvol_calib.py that calibrates, reprices with fpde.price_vanilla_surface, and checks that the first-expiry vol RMSE stays below the calibration tolerance.

#2 With 'none' extrapolation, interpolation returns NaN on the first and last nodes, so discount-factor curves give NaN at the valuation date High
sdevpy/maths/interpolation.py · lines 294–298  ·  sdevpy/market/yieldcurve.py · lines 121, 123

What happens: Interpolation.value sends a point to the extrapolator when it is within eps of the grid's ends: 

below = (x < self.x_grid[0] + self.eps)     # True exactly on the first node
above = (x > self.x_grid[-1] - self.eps)    # True exactly on the last node

For interp_var='discount' or 'log_discount', InterpolatedYieldCurve uses l_extrap='none', r_extrap='none', and NoneExtrapolator.value returns NaN. Reproduced in the current code: curve.discount(valdate) returns nan for both variables, and so does discount(last pillar). The mid-curve values (0.98) are fine. FixingHandler(interpolate=True) uses the same 'none' mode, and returns NaN silently outside the fixing range.

Why it's bad: Both options are supported and documented, and they fail on the most common query of all: the DF at t=0, or a cashflow on a curve pillar. NaN spreads silently through PVs. The stored test curves use zerorate, which is why no test catches this.

Fix: hand off to the extrapolator only strictly outside the grid. The interpolators return the node value exactly on the nodes, so flat and linear extrapolation results do not change.

# interpolation.py, Interpolation.value
-        below = (x < self.x_grid[0] + self.eps)
-        above = (x > self.x_grid[-1] - self.eps)
+        below = (x < self.x_grid[0] - self.eps)
+        above = (x > self.x_grid[-1] + self.eps)

Add assert curve.discount(valdate) == 1.0 and a last-pillar check for all three interp_var values in test_yieldcurves.py.

#4 The package declares requires-python >= 3.10, but DatedRepository[T] uses 3.12-only syntax, so the whole pricing stack fails to import on 3.10 and 3.11 High
sdevpy/utilities/datedrepository.py · line 7  ·  pyproject.toml · line 13

What happens: class DatedRepository[T]: is PEP 695 generic syntax, and it is a SyntaxError before Python 3.12. market/repository.py and calibration/repository.py import it, and so, transitively, do pricingcontext, montecarlo.payoffs.basic, utilities.book, mcpricer, lvsection_calib and fx_volcalib. pip will install the package on 3.10 or 3.11 because the metadata allows it, and every one of those imports will then fail.

Why it's bad: The declared contract is broken for two of the four supported Python versions, and ruff's target-version = "py313" hides the problem.

Fix: pick one of these options, and don't leave the two out of step.

# Option A: pyproject.toml line 13 (the code already targets 3.13 via ruff)
-requires-python = ">=3.10"
+requires-python = ">=3.12"

# Option B: datedrepository.py, keep 3.10 support
+from typing import Generic, TypeVar
+T = TypeVar("T")
-class DatedRepository[T]:
+class DatedRepository(Generic[T]):
#5 The default data root is the test-fixture folder, so the examples overwrite the stored calibrations that the tests read Medium
sdevpy/datapaths.py · line 11  ·  examples/volatility/ex_lv_section_calib.py · line 38  ·  ex_lv_dupire_calib.py · line 78  ·  ex_iv_calib.py · line 81  ·  fx_volcalib.py · line 268  ·  pyproject.toml · line 38

What happens: root_path() falls back to Path(__file__).parent / "tests" / "data" when SDEVPY_DATA is unset. default_calibration_repository() writes through to that folder. ex_lv_section_calib.py runs with force_restart=True and then calib.save_localvol('ABC', 'BiExp', lv), which replaces tests/data/calibdata/localvol/ABC/20251215-000000.BiExp.json. That is the file test_localvol.py, test_calibrationdata.REF_CALIB and the LV calibration tests read. The same holds for the Dupire and IV examples, their three notebooks, and the fx_volcalib demo. Commit 332ac74 shows this already happening: a fixture (ABC/…Matrix.json) was rewritten by an example run. package-data also ships all of tests/data (26 MB, including GPT weights) in the wheel, and in an installed package those writes go into site-packages.

Why it's bad: Running a demo silently changes the regression baseline, and a real deployment writes its calibrations into the installed test data.

Fix: point the tests at the fixtures explicitly, and make the library default a user folder:

# datapaths.py
-    return Path(__file__).parent / "tests" / "data"
+    return Path.home() / ".sdevpy" / "data"

# sdevpy/tests/conftest.py (top of file, before any test module builds a repository)
+import os
+from pathlib import Path

# pyproject.toml line 38

If you regenerate fixtures deliberately, do it through a flag in the examples, for example REGENERATE_FIXTURES = False guarding the save_* call, so it can't happen by accident.

#7 Equity path-dependent payoffs default to the US federal holiday calendar instead of an exchange calendar Medium
sdevpy/montecarlo/payoffs/basic.py · lines 234, 464  ·  exotics.py · lines 14, 73  ·  sdevpy/utilities/scalendar.py · line 412

What happens: Average, Variance, WorstOfBarrier and make_asian_option all default to cdr="USD", which maps to holidays.US (federal holidays). Checked against make_calendar("NYSE"): Good Friday (2026-04-03) is a USD business day but an NYSE holiday, while Columbus Day (2026-10-12) and Veterans Day (2026-11-11) are USD holidays but NYSE trading days.

Why it's bad: Averaging and variance schedules include a day with no fixing and skip two days that do have fixings. This changes n_returns and the variance annualisation. For a trade struck in the past, md.get_fixings raises "Fixing not found" on Good Friday.

Fix: default to the exchange calendar, and cache calendars, because building an mcal calendar takes about 0.15 s:

# basic.py:234, basic.py:464, exotics.py:14, exotics.py:73
-    ..., freq="1D", cdr="USD"):
+    ..., freq="1D", cdr="NYSE"):

# scalendar.py, make_calendar
+@functools.lru_cache(maxsize=None)
 def make_calendar(name: str, start_year: int=2000, end_year: int=2100):

A better long-term fix is to take the calendar from the underlying's static data rather than from a keyword default.

#10 The FX vol calibrator builds its forward without the spot-date adjustment, so it disagrees with FxForwardCurve Low
sdevpy/volatility/fx/fx_volcalib.py · lines 76–77  ·  sdevpy/market/fx/fxforward.py · line 40

What happens: The calibrator computes fwd = self.spot * df_f / df_d, where self.spot is the quoted spot (which settles at T+2) and the DFs run from valdate to settlement. FxForwardCurve.load_calibrated handles this correctly: it first moves spot back to t=0 with spot0 = spot / P_f(spot_date) · P_d(spot_date). Reproduced on the USDJPY test data at 1M: the calibrator's forward is 150.18737 and CalibrationDataSet.get_fx_forward_curve gives 150.17750, a difference of about 1 pip.

Why it's bad: The ATM and delta strikes are solved against a forward that the pricing curve does not reproduce. The error is small but systematic, and it grows with the rate differential. The logic is also duplicated even though CalibrationDataSet already provides the forward curve.

Fix: use the dataset's forward curve, and quote the DFs from spot to settlement:

# _fetch_market_data
+        self.fwd_curve = calib.get_fx_forward_curve(self.pair, mkt)
+        self.spot_date = self.fwd_curve.spot_date()

# calibrate_tenor, lines 76-77
-        df_f, df_d = self.forcurve.discount(settlement), self.domcurve.discount(settlement)
-        fwd = self.spot * df_f / df_d
+        df_f = self.forcurve.discount(settlement) / self.forcurve.discount(self.spot_date)
+        df_d = self.domcurve.discount(settlement) / self.domcurve.discount(self.spot_date)
+        fwd = self.fwd_curve.value(settlement)   # == self.spot * df_f / df_d

This moves the calibrated strikes by a fraction of a basis point. No test in sdevpy/tests currently exercises FxVolCalibrator, so add one that checks fwd equals calib.get_fx_forward_curve(pair, mkt).value(settlement).
