The working tree is clean and all 633 tests pass. Five of the 20th review's ten findings are fully resolved and one more partly. The grade drops because this time I checked the numbers against theory, and three existing pricing defects showed up, all reproduced by running the code. (1) The MC engine simulates on a coarse uniform grid and linearly interpolates paths to event dates, so a 1-year daily variance swap under a flat 20% vol prices at a fair variance of 98 instead of about 400 (9.9% vol instead of 20%). The same interpolation overprices a daily-monitored barrier by about 6%. (3) Interpolations with 'none' extrapolation return NaN exactly at their first and last nodes, which makes discount-factor yield curves return NaN at the valuation date. None of these are recent regressions. They survived because the tests compare against stored snapshots rather than analytical values. For each of the top three, I confirmed the proposed fix against the current code in a scratch script.

#1 MC paths are linearly interpolated between coarse grid points, so variance swaps are ~75% underpriced and daily barriers are overpriced Critical
sdevpy/montecarlo/mcpricer.py · lines 17–22, 44, 124–125  ·  sdevpy/montecarlo/payoffs/basic.py · lines 478–497 (Variance)  ·  exotics.py · lines 26–44 (WorstOfBarrier)

What happens: build_timegrid simulates on np.linspace(0, max_t, n_timesteps + 1) (default 50 steps), ignoring the event dates. interp_paths then fills every daily event date by straight-line interpolation between two grid points. A straight line has no variance between its nodes, so when a daily schedule spans m days per grid step, the sum of squared daily log-returns in Variance.evaluate comes out about m times too small. Likewise, WorstOfBarrier only "sees" the barrier at the 50 grid nodes, not every day.

Reproduced (1Y variance swap from valdate on ABC, flat ConstantLocalVol(0.20), Sobol 4,000 paths; fair value = PV / DF):

n_timesteps=  10  fair variance=  21.51  (vol  4.64%)   worst-of barrier PV=13.8680
n_timesteps=  50  fair variance=  97.88  (vol  9.89%)   worst-of barrier PV=12.5691   # default
n_timesteps= 250  fair variance= 269.40  (vol 16.41%)   worst-of barrier PV=12.0116
n_timesteps= 365  fair variance= 401.78  (vol 20.04%)   worst-of barrier PV=11.8372   # correct: ~400

Why it's bad: The price depends on a numerical setting that should not matter, and the default is badly wrong. Every variance swap and daily-monitored barrier priced through price_book carries this error, and nothing warns about it. The reference value in test_mc.py:62 (-53.11 for a 14-vol strike, i.e. ~12% realised under 20% vol) locks the wrong number in.

Fix — simulate on the union of the uniform grid and the event times, so every event date is an exact grid node (interpolation weights become 0/1). In mcpricer.py:

from sdevpy.utilities import timegrids, timer, algos

def build_timegrid(valdate, eventdates, config) -> npt.ArrayLike:
    max_date = eventdates.max()
    max_t = timegrids.model_time(valdate, max_date)
    disc_tgrid = timegrids.build_timegrid(0.0, max_t, config)
    return disc_tgrid
    """ Uniform grid refined with every event time, so events fall exactly on nodes """
    event_times = timegrids.model_time(valdate, eventdates)
    base = np.linspace(0.0, float(np.max(event_times)), config.n_timesteps + 1)
    return algos.unique_sorted(np.concatenate([base, event_times]), atol=1e-10)

I checked this by monkeypatching it in a scratch script: fair variance becomes 401.78 (10 steps) / 401.82 (50 steps), and the barrier PV becomes 11.83 / 11.81, independent of n_timesteps, with no noticeable runtime cost. Then update the snapshot in test_mc and add an analytical check (see #6). Keep interp_paths for events that genuinely fall between nodes, but log a warning when 0 < w1 < 1, since that should now never happen.

#2 LV section calibrator runs the first expiry's PDE from t = 0, the pricer from t = 1/365: calibration and repricing disagree High
sdevpy/volatility/localvol/lvsection_calib.py · lines 194, 284–286, 301

What happens: LvObjectiveBuilder.__init__ sets self.start_time = 0.0 (line 194). set_expiry(0, …) builds the step grid from that value (line 284). initialize() only sets start_time = FWD_PDE_START_TIME later, on the first objective call (line 301), after the grid already exists. The mollified density already represents time 1/365, so slice 0 diffuses for one extra day. forwardpde.calculate_densities, used by price_vanilla_surface and NumericalImpliedVol, correctly starts at FWD_PDE_START_TIME.

Reproduced (flat 20% VSVI LV, 30-day expiry, Rannacher 100×400, straddles converted to vols at 90/100/110% strikes):

calibrator step grid for slice 0 starts at 0.0   (pricer starts at 0.00274)
calibrator PDE vols   [0.20466 0.20321 0.20266]
pricer PDE vols       [0.20142 0.19991 0.19930]

Why it's bad: The optimiser fits the market with a PDE that has one extra day of variance, so the calibrated first LV section comes out too low. Repricing the calibration instruments with the production pricer then misses the market by roughly 30 bp of vol at a 1-month expiry, and more for shorter ones. The later slices inherit a density that was built with this first section.

Fix — set the real start time at construction so the first grid is built correctly:

        self.pde_config = pde_config
        self.start_time = 0.0
        self.start_time = fpde.FWD_PDE_START_TIME # Must match forwardpde.calculate_densities
        self.penalty_type = penalty_type

and drop the assignment on line 301 of initialize(). With this change, the calibrator and pricer vols above match to 5 decimals (checked in a scratch script).

#3 'none' extrapolation returns NaN on the first and last nodes: discount-factor yield curves give NaN at valdate and the last pillar High
sdevpy/maths/interpolation.py · lines 294–298  ·  sdevpy/market/yieldcurve.py · lines 118–125

What happens: Interpolation.value treats a point as extrapolated when x < x_grid[0] + eps or x > x_grid[-1] - eps. That test includes the end nodes themselves, so any interpolation built with l_extrap='none' / r_extrap='none' returns NaN at its own data points. InterpolatedYieldCurve uses exactly that for its 'discount' and 'log_discount' variables. Reproduced: 

zerorate      DF(valdate)=1.0   DF(6M)=0.97985  DF(last pillar)=0.92
discount      DF(valdate)=nan   DF(6M)=0.98005  DF(last pillar)=nan
log_discount  DF(valdate)=nan   DF(6M)=0.97985  DF(last pillar)=nan
cubicspline + 'none' at nodes [0, 1, 2] -> [nan, 2.0, nan]

Why it's bad: A cash flow paid on the last curve pillar, or a DF requested at t=0 (which pricers do routinely), silently becomes NaN and spreads through the PV. The test curves happen to use zerorate with flat extrapolation, so nothing catches it.

Fix — only strictly outside points are extrapolated. In Interpolation.value:

        below = (x < self.x_grid[0] + self.eps)
        above = (x > self.x_grid[-1] - self.eps)
        below = (x < self.x_grid[0] - self.eps)
        above = (x > self.x_grid[-1] + self.eps)

I checked this in a scratch subclass: 'none' gives [1.0, 0.98, 0.95, nan] at [0, 1, 2, 2.5], and flat extrapolation results are unchanged. Make the same change in FlatExtrapolator.value (lines 253–254) and LinearInterpolator.value (lines 210–211) for consistency. Add a test that evaluates every extrapolation type exactly at the end nodes.

#4 Flat local vols return 0 when log-moneyness is passed as integers (np.full_like keeps the int dtype) Medium
sdevpy/volatility/localvol/localvol.py · line 271 (FlatLocalVolSection.value)  ·  line 332 (ConstantLocalVol.value)

Reproduced:

ConstantLocalVol(0.2).value(1.0, 0)            -> 0          # expected 0.2
ConstantLocalVol(0.2).value(1.0, [0, 1])       -> [0 0]
ConstantLocalVol(0.2).path_vol(1.0, [0, 1])    -> [0. 0.]
VectorLocalVol([.5, 1], [.2, .3]).value(.7, [0, 1]) -> [0 0]

Why it's bad: np.full_like(logm, self.vol) creates an array with logm's dtype, so 0.2 is truncated to 0 without any error. Internal callers happen to pass floats, but lv.value(t, 0) for an ATM check is a natural call to make, and it returns a zero vol that feeds PDE grids and MC diffusion. The same pattern appears in TsSvi1/TsSvi2.calculate (np.full_like(k, np.nan)), where integer strikes turn the NaN "invalid parameters" signal into 0, with only a RuntimeWarning (verified: np.full_like(np.array([90, 100]), np.nan) → [0 0]).

Fix — force a float dtype:

        return np.full_like(logm, self.vol)
        return np.full(np.shape(logm), self.vol, dtype=float)

and in tssvi1.py:39 / tssvi2.py:34: np.full(np.shape(k), np.nan, dtype=float).

#5 Equity path-dependent payoffs default to the US federal holiday calendar, not an exchange calendar Medium
sdevpy/montecarlo/payoffs/basic.py · lines 234, 464  ·  exotics.py · lines 14, 73  ·  sdevpy/utilities/scalendar.py · line 412

What happens: Average, Variance, WorstOfBarrier and make_asian_option default to cdr="USD", which maps to holidays.US (federal/settlement holidays). Verified: 

Good Friday 2026-04-03 in 'USD' schedule:  True    # NYSE is closed, no fixing exists
Columbus Day 2026-10-12 in 'USD' schedule: False   # NYSE is open, a real fixing is skipped
Good Friday in 'NYSE' schedule:            False

Why it's bad: For a seasoned variance swap or Asian, set_valuation_date asks the fixing handler for Good Friday and raises ValueError("Fixing not found") on real data. It also drops genuine observation days, so the averaging and variance counts (n_samples, n_returns) no longer match the term sheet. The test fixing file was generated with the same calendar, which hides the problem.

Fix — make the observation calendar an explicit, exchange-based argument. make_calendar already routes non-currency names to pandas_market_calendars:

    def __init__(self, name, start, end, freq="1D", cdr="USD"):
    def __init__(self, name, start, end, freq="1D", cdr="NYSE"):  # observation (exchange) calendar

Better still, drop the default and look it up per underlying (e.g. from the spot/forward data files), so an index listed elsewhere gets its own exchange calendar.

#6 Pricing tests compare against stored snapshots instead of analytical benchmarks, which is how #1–#3 went unnoticed Medium
sdevpy/tests/test_mc.py · lines 62–63  ·  test_localvol_calib.py  ·  test_interpolation.py

What happens: test_mc asserts five PVs to atol=1e-8 against hard-coded numbers, one of which is the underpriced variance swap (-53.11327812897). Nothing in the suite checks that the MC reproduces Black-Scholes, that a flat-vol variance swap is worth σ², that the calibrator and pricer agree, or what the interpolators return at their end nodes.

Why it's bad: A snapshot test catches changes, not errors. Fixing #1 will "break" test_mc, while the bug itself passed CI for as long as it existed.

Fix — add a few cheap invariants next to the snapshots, e.g. in test_mc.py:

def test_variance_swap_flat_vol():
    valdate, expiry = dt.datetime(2025, 12, 15), dt.datetime(2026, 12, 15)
    book = bk.Book()
    book.add_trades([Trade(Instrument(cashflow_legs=[[cfl.Cashflow(Variance('ABC', valdate, expiry), expiry)]]))])
    ctx = default_pricing_context()
    pv = price_book(valdate, book, ctx, rng_type='sobol', n_paths=4096,
                    lv_map={'ABC': ConstantLocalVol(0.20)})['pv'][0]
    df = ctx.calib_provider.get_yieldcurve(book.csa_curve_id, valdate).discount(expiry)
    assert abs(pv / df - 400.0) < 10.0   # 10000 * 0.2^2, MC tolerance

Similarly: an MC vanilla against black.price, LvObjectiveBuilder vs fpde.price_vanilla_surface on a flat LV (#2), and every extrapolation type evaluated at the end nodes (#3).

#9 Calibration-data read methods create directories on disk as a side effect Low
sdevpy/calibration/fileprovider.py · lines 56, 62, 68

What happens: impliedvol_data_file, localvol_data_file and fxvol_data_file call folder.mkdir(parents=True, exist_ok=True), and get_impliedvol_data, get_localvol_data and get_fxvol_data go through them. Every lookup for a name or date with no data leaves an empty folder behind. With no SDEVPY_DATA set, the root is sdevpy/tests/data inside the installed package.

Why it's bad: A query should not change state. It can fail with PermissionError on a read-only install (site-packages, containers), and it litters the data tree with empty folders that make "does data exist?" checks misleading.

Fix — build the path without touching disk, and create the folder only when writing:

    def localvol_data_file(self, name, date, model_name, create: bool = False) -> Path:
        folder = self.root / 'localvol' / name
        folder.mkdir(parents=True, exist_ok=True)
        if create:
            folder.mkdir(parents=True, exist_ok=True)
        return folder / (date.strftime(dts.DATE_FILE_FORMAT) + "." + model_name + ".json")

and pass create=True from the dump paths (e.g. fx_volcalib.py:265 and the LV/IV calibration examples).
