#1 Two whole subpackages — volatility/fx and instruments — have no __init__.py, and are silently dropped by pyproject.toml's own package discovery Critical
sdevpy/volatility/fx/  ·  sdevpy/instruments/  ·  pyproject.toml · lines 30-32 Verified: ran the project's own setuptools.find_packages(where='.', include=['sdevpy*']) against the checked-in pyproject.toml

Why it's bad: Every other package directory in the repo has an __init__.py (even if empty) — sdevpy/market/fx/__init__.py, sdevpy/volatility/localvol/__init__.py, sdevpy/volatility/impliedvol/__init__.py, all present. sdevpy/volatility/fx/ and sdevpy/instruments/ are the only two exceptions in the whole non-thirdparty tree. Running the exact discovery call pyproject.toml is configured to use: 

from setuptools import find_packages
pkgs = find_packages(where='.', include=['sdevpy*'])
print('sdevpy.volatility.fx' in pkgs)   # False
print('sdevpy.instruments'   in pkgs)   # False

confirms both are excluded. In the dev checkout this is invisible — Python 3's implicit namespace packages mean import sdevpy.volatility.fx.fx_volcalib still works when running from source, which is exactly why nothing caught it. But any real distribution — pip install ., a built wheel, a PEP 660 editable install, a CI artifact — uses this exact discovery call, and would ship without fx_volcalib.py, fx_volinterpolation.py, fx_deltastrike.py, fx_vannavolga.py, fx_strangle.py and fx_calib_batch.py — the entire FX options surface this session's work went into — plus instruments/constants.py, which sdevpy/pde/forwardpde.py imports directly (OptionType, string_to_optiontype), so the PDE pricer would fail to import too.

Fix:

touch sdevpy/volatility/fx/__init__.py
touch sdevpy/instruments/__init__.py
# both empty, matching every sibling package's __init__.py in this repo
#2 The real Monte-Carlo pricer's local-vol resolution is broken two independent ways for any name that isn't a test fixture High
sdevpy/calibration/provider.py · lines 24-31, 34-58  ·  sdevpy/volatility/localvol/localvol_factory.py · lines 50-53 Verified: read the current file; first half re-confirms the 16th review's #1 (still open, 16 days later)

Why it's bad: mcpricer.py's real pricing entry point, price_book, calls get_local_vols → get_localvol_or_new for every name in the book with no explicit model_name. Two things go wrong on that path: 

# provider.py — only three names are known, and they are the TEST fixture names
name_model_map = {'ABC': 'BiExp', 'KLM': 'VSVI', 'XYZ': 'Matrix'}
# sdevpy/tests/data/calibdata/localvol/{ABC,KLM,XYZ} -- exactly these three

model_name = (name_model_map.get(name, None) if model_name is None else model_name)
if model_name is None:
    raise ValueError(f"No model name specified for name: {name}")

Any real underlying ("SPX", "AAPL", whatever a real book holds) raises immediately. And even with an explicit model_name, the second half is worse — it's silent rather than loud. get_localvol_or_new's comment says "Try to get it from calibration provider, None if absent", but the factory it calls through never returns None: 

# localvol_factory.py
def get_localvol_from_data(data, new_t_grid=None):
    if data is None:
        raise ValueError('LocalVol data is None')  # raises instead of letting the caller fall back

so get_localvol_or_new's if lv is None: lv = lvf.get_localvol_new(...) branch — the one line that is supposed to create a fresh model when no calibration file exists yet, which is the entire reason the function exists — is unreachable dead code. Pricing any name with no stored local-vol file crashes with ValueError('LocalVol data is None') instead.

Fix: Check for missing data before it reaches the raising factory call, and stop hardcoding test names as the production default:

def get_localvol_or_new(name, date, model_name, cal_prov, t_grid=None, force_new=False):
    if model_name is None:
        raise ValueError(f"No model name specified for name: {name}")  # no silent fixture map

    lv = None
    if not force_new:
        data = cal_prov.get_localvol_data(name, date, model_name)  # check directly, don't go through the raising path
        if data is not None:
            lv = lvf.get_localvol_from_data(data, t_grid)

    if lv is None:
        log.info(f"Initializing new LV for {name}")
        lv = lvf.get_localvol_new(t_grid, model_name)
    return lv
#3 WorstOfBarrier's knock-in/out result silently depends on which other trades happen to share its pricing book High
sdevpy/montecarlo/payoffs/exotics.py · lines 19-45  ·  sdevpy/utilities/book.py · lines 43-52 Verified: still present, unchanged from the 16th review's #2

Why it's bad: set_valuation_date registers only the expiry as this trade's own event date: 

def set_valuation_date(self, valdate, md):
    if self.expiry < valdate:
        raise ValueError("Past trade found")
    self.eventdates = [self.expiry]  # no interim monitoring dates registered

but evaluate() monitors the barrier over the entire simulated time axis of mkt_state.event_paths — which is the whole book's merged event-date grid (built by Book.set_valuation_date via list_instrument_eventdates across every instrument in the book), not this trade's own dates: 

paths = mkt_state.event_paths          # the BOOK's merged grid, not this trade's own
spot_all = self.paths_for_all(paths)
min_path = spot_all.min(axis=2)
knocked = (min_path < self.barrier).any(axis=1)  # checked at every date in that merged grid

Pricing this trade alone monitors the barrier at essentially one time point (the expiry). Adding an unrelated Asian option with a dense daily fixing schedule to the same book adds all of those extra dates to the shared grid, and this trade's knock result changes purely because of another trade's presence — with no error and no hint in the API that the dependency exists.

Fix: Register the trade's own intended monitoring dates in set_valuation_date (e.g. a daily/weekly grid from trade start to expiry) and index spot_all using this trade's own date indices, mirroring how Average/Variance in the same file resolve theirs.

#4 fx_spot_date silently skips the USD calendar for six lag=1 crosses, contradicting its own docstring High
sdevpy/market/fx/fxforward.py · lines 87-101 Verified: still present, unchanged from the 16th review's #3

Why it's bad: The docstring is explicit that crosses always need the USD calendar: 

def fx_spot_date(date, forccy, domccy):
    """ ... Crosses (neither leg USD) only need the first hop good in the pair's own
        centers, then require USD too, since crosses settle via two USD legs. """
    lag = fx_spot_lag(forccy, domccy)
    pair_cal = make_calendar(f"{forccy},{domccy}")
    if 'USD' in (forccy, domccy):
        return pair_cal.add_business_days(date, lag)

    settle_cal = make_calendar(f"{forccy},{domccy},USD")  # built...
    shifted_date = pair_cal.add_business_days(date, 1)
    return settle_cal.add_business_days(shifted_date, lag - 1) if lag > 1 else shifted_date  # ...but never used when lag == 1

FX_SPOT_LAG_OVERRIDES sets lag = 1 for exactly six cross pairs with no USD leg (CAD/KZT, CAD/PHP, CAD/TRY, KZT/PHP, KZT/TRY, PHP/TRY). For those six, settle_cal is built and then thrown away — the ternary falls through to shifted_date, validated only against pair_cal. If that settlement day is a US holiday but a good day for both actual currencies, the function returns a date that isn't a valid USD settlement day, directly contradicting the convention its own docstring states. No test in test_fxdata.py exercises any of the six affected pairs.

Fix: Always route through settle_cal, dropping the special case:

return settle_cal.add_business_days(shifted_date, lag - 1) if lag > 1 else shifted_date
return settle_cal.add_business_days(shifted_date, max(lag - 1, 0))
#5 Production data providers depend on the test package for their default paths — one file at the 16th review, now four across three subsystems High
sdevpy/market/fileprovider.py · line 20  ·  sdevpy/calibration/fileprovider.py · line 5  ·  sdevpy/llms/llmfactory.py · line 9  ·  sdevpy/llms/gpt_model.py · line 121 Verified: grep -rn "from sdevpy.tests import conftest" across the whole tree

Why it's bad: The 16th review flagged this in market/fileprovider.py alone (Medium, #9). It is still there, unfixed, and the same pattern has since spread to three more files: 

# market/fileprovider.py, calibration/fileprovider.py
from sdevpy.tests import conftest
class MarketDataFileProvider(MarketDataProvider):
    def __init__(self, root=None):
        self.root = (Path(root) if root is not None else conftest.marketdata_path())

# llms/llmfactory.py (module level), llms/gpt_model.py (function level)
from sdevpy.tests import conftest as tst

Every one of these is a real production code path — MarketDataFileProvider() and CalibrationDataFileProvider() are both constructed with no root argument from default context builders elsewhere in the codebase, and the LLM factory's model config resolution goes through tst. the same way. Any packaging or deployment scenario that excludes sdevpy/tests (issue #1 above shows the discovery config for this exact repo already drops two other directories) would break every one of these imports at module load time, not at first use.

Fix: Move default data-root resolution into a non-test config/settings module (e.g. sdevpy/settings.py, which already exists), and have conftest.py import from there instead of the reverse — across all four files, not just the one flagged last time.

Fix: Add both to dependencies in pyproject.toml (or, if GPT/PyTorch support is meant to be optional, move them into an [project.optional-dependencies] extra and guard the imports accordingly).

#8 Golden-master test reference values are rebased in place with the old value left commented out, unexplained Medium
sdevpy/tests/test_pde.py · lines 60-61, 81-82  ·  also test_mc.py, test_localvol_calib.py, test_impliedvol.py, test_localvol.py, test_marketdata.py Verified: still present, unchanged from the 16th review's #6

Why it's bad: The same pattern recurs across the numerical core of the test suite: 

pde_ref = np.asarray([2.70428011, 10.60023123, 21.44746433, 60.16740876, 132.39777875, 279.0919945])
# pde_ref = np.asarray([2.70606853, 10.6012976, 21.44167511, 60.14815888, 132.34671851, 279.04775693])  # old value

Nothing in the test or its history (as far as the file itself shows) says whether a given rebase reflects a genuine fix or papers over a regression. In test_pde.py the file's own independent closed-form reference makes it possible to tell (the new values are closer), but test_mc.py has no such cross-check, so there is no way to tell from the test alone. Left unexplained across six files, this weakens confidence that these tests would flag a real future regression, since "matches the last observed output" and "matches the true answer" become indistinguishable in the diff.

Fix: When a reference value changes, delete the old one (git history preserves it already) and add a one-line comment stating why it changed, e.g. # updated after fixing #N — bug caused Y% error vs. closed-form.

#9 Large parts of the codebase have zero automated test coverage, including the buggiest module in this review Medium
sdevpy/instruments/  ·  sdevpy/montecarlo/payoffs/exotics.py  ·  sdevpy/machinelearning/pytorch/*  ·  sdevpy/llms/gpt/*  ·  sdevpy/tensorflow/* Verified: 36 files under sdevpy/tests against 124 non-test, non-thirdparty source files; no test_*.py references WorstOfBarrier, instruments, or the pytorch/gpt/tensorflow trees

Why it's bad: WorstOfBarrier (issue #3 above) is exactly the kind of nontrivial, path-dependent payoff logic that a unit test would have caught immediately — pricing it alone versus in a book with an Asian option added would have produced two different numbers for the same trade, with no test anywhere to notice. The same gap extends to instruments/constants.py (imported directly by the PDE pricer, per issue #1), and to three entire subsystems (machinelearning/pytorch, llms/gpt, tensorflow) with no test_*.py file touching them at all.

Fix: Prioritize a test_exotics.py that prices WorstOfBarrier alone and in a book with an unrelated dense-schedule trade, and asserts the two prices match — that alone would have caught issue #3 directly. Follow with minimal smoke tests for instruments/ and the three untested subsystems.
