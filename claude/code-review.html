#1 Andersen scheme's drift-correction term is always exactly zero due to array aliasing — silently wrong Monte-Carlo prices Critical
sdevpy/volatility/impliedvol/models/fbsabr.py · lines 72, 76, 82-84  ·  sdevpy/volatility/impliedvol/models/mcsabr.py · lines 74-78, 95-97

Why it's bad: In fbsabr.py, scheme='Andersen' is the default value in price(...)'s signature (line 11): 

vols = vol
abs_f = np.maximum(np.abs(spot), floor)

# Evolve vol
vol *= np.exp(-0.5 * nu2 * dt + nu * dz1)

# Evolve spot
elif scheme == 'Andersen':
    vole = vol
    spot = spot + alpha * abs_f**beta * (sqrtmrho2 * vols * dz0 + rho / nu * (vole - vols))

vols = vol binds a reference to the same ndarray, not a copy. The next line, vol *= np.exp(...), mutates that array in place, so vols silently becomes the post-update vol too. Then vole = vol aliases the same already-updated array again, so vole - vols is identically 0.0 for every path and every time step — the entire drift-correction term of the Andersen discretization vanishes, and the diffusion term uses the new vol instead of the old vol. This produces silently wrong Monte-Carlo prices on every call that doesn't override scheme.

The identical pattern is repeated in mcsabr.py's 'Andersen' branch (reachable when a caller explicitly requests it — the default there is 'LogAndersen', which correctly avoids the bug by writing vols = vol * avolc, a genuine new array via multiplication):

else:
    vols = vol
...
vol *= np.exp(-0.5 * nu2 * dt + nu * dz1)
...
elif scheme == 'Andersen': # Does not work well
    vole = vol
    spot += alpha * np.abs(spot)**beta * (sqrtmrho2 * vols * dz0 + rho / nu * (vole - vols))

The existing # Does not work well comment on the mcsabr.py branch strongly suggests this was already observed and misattributed to the model rather than to this aliasing bug.

Fix:

vols = vol
vols = vol.copy()
#2 Monte-Carlo pricer crashes on any multi-leg trade whose legs have different cashflow counts Critical
sdevpy/montecarlo/mcpricer.py · line 176

Why it's bad:

results['pv'] = trade.notional * np.asarray(leg_cf_pvs).sum(axis=1).sum()

leg_cf_pvs is a list of per-leg lists of scalar cashflow PVs. np.asarray() requires every leg to have the same number of cashflows to form a rectangular array. Any instrument whose legs don't line up — a swap with quarterly fixed vs. monthly floating cashflows, or any leg carrying an extra notional-exchange or fee cashflow — raises: 

ValueError: setting an array element with a sequence. The requested array has an
inhomogeneous shape after 1 dimensions.

This crashes MonteCarloPricer.build() for realistic ragged-leg trades; it goes unnoticed because test_mc.py's trades all happen to have equal-length legs.

Fix: sum each leg first, then sum the leg totals, instead of forcing a ragged list into a rectangular array:

results['pv'] = trade.notional * np.asarray(leg_cf_pvs).sum(axis=1).sum()
results['pv'] = trade.notional * sum(sum(leg) for leg in leg_cf_pvs)
#3 ThetaScheme's docstring has theta=0.0 and theta=1.0 exactly backwards High
sdevpy/pde/pdeschemes.py · lines 31-70 (docstring at 32-35), cross-checked against ImplicitScheme (73-98) and ExplicitScheme (101-121)

Why it's bad:

class ThetaScheme(PdeScheme):
    """ Mixing scheme with particular sub-cases:
            Theta = 0.0: Implicit
            Theta = 0.5: Crank-Nicolson
            Theta = 1.0: Explicit """

Tracing the actual coefficients: at theta=1.0, one_m_theta_dt_2 is 0, so the explicit right-hand side reduces to y = p (unmodified), and theta_dt_2 * b/a/c exactly reproduce ImplicitScheme's tridiagonal coefficients — ThetaScheme(1.0) is ImplicitScheme. Symmetrically, at theta=0.0 the tridiagonal matrix collapses to the identity and y exactly reproduces ExplicitScheme's output. So theta=0.0 is Explicit and theta=1.0 is Implicit — precisely the opposite of what the docstring states. This is reachable through PdeConfig(scheme='theta', theta=<value>) via the scheme() factory (line 131): a caller who reads the docstring and sets theta=0.0 expecting unconditional stability instead silently gets the unconditionally-unstable explicit scheme.

Fix: Swap the docstring's labels to match the code (0.0 → Explicit, 1.0 → Implicit), and add a test pinning ThetaScheme(1.0)/ThetaScheme(0.0) against ImplicitScheme/ExplicitScheme output to prevent silent re-drift.

#4 Calendar.make_schedule produces drifting roll dates — each period anchors off the previous adjusted date instead of the original schedule High
sdevpy/utilities/scalendar.py · lines 70-75

Why it's bad:

def make_schedule(self, start, end, term, convention=BDC.F, convert_to_datetime=False):
    """ Simplified schedule generation for now (forward) """
    schedule_dates, d = [], self.adjust(start, convention)
    while d <= end:
        schedule_dates.append(d)
        d = self.adjust(d + dts.period(term), convention)

Each new roll date is computed by adding the period to the previously business-day-adjusted date, not to the original unadjusted anchor. Business-day adjustments therefore compound period over period: a monthly schedule anchored on 2024-01-31 drifts to 2024-12-04 by year end once weekend/holiday adjustments accumulate, instead of tracking end-of-month. Contrast with make_schedule_fancy in the same file (lines 86-134), which correctly generates all unadjusted roll dates first and adjusts once at the end — the fix pattern already exists two methods away. make_schedule is public API; any caller building a schedule with it gets silently corrupted roll dates with no error.

Fix: Track the raw unadjusted anchor separately, adding the period to that on every iteration, and adjust only the date that gets appended to the schedule — mirroring make_schedule_fancy's two-pass approach.

#5 FX pairs missing from a hardcoded 11-entry table are silently treated as "not inverted" High
sdevpy/timeseries/timeseriestools.py · lines 77-85, used at lines 106, 113

Why it's bad:

def is_inverted_quote(key):
    is_inverted = False
    bbg_dict = {'EURUSD Curncy': False, ... 'CNHUSD Curncy': True} # 11 entries total
    is_inverted = bbg_dict.get(key)
    return is_inverted

For any ticker not in the 11-entry dictionary (e.g. 'MXNUSD Curncy', 'BRLUSD Curncy', 'HKDUSD Curncy'), .get(key) returns None. create_position uses this as if is_inverted_quote(name_list[x]): — None is falsy, so the pair is silently treated as not inverted. This flows directly into weights_market_convention and usd_amount, the position-sizing/direction output consumed by cointegration.py, giving a silently wrong notional and sign for any currency outside the hardcoded list — with no error or warning raised anywhere.

Fix: Raise on an unrecognized ticker instead of defaulting through a falsy None: if key not in bbg_dict: raise ValueError(f"Unknown FX ticker: {key}").

#6 implied_vol_newton can silently return NaN vols for deep ITM/OTM strikes instead of failing loudly High
sdevpy/analytics/black.py · lines 79-93

Why it's bad:

for _ in range(max_iter):
    s = vol * sqrt_t
    d1 = np.log(fwd / strike) / s + 0.5 * s
    vega = fwd * norm.pdf(d1) * sqrt_t
    diff = price(expiry, strike, is_call, fwd, vol) - fwd_price
    vol -= diff / vega
    vol = np.maximum(vol, 1e-8)
    if np.all(np.abs(diff) < tol):
        converged = True
        break

if not converged:
    log.warning("max_iter reached without full convergence")

return vol

For deep ITM/OTM strikes (common on real vol surfaces), vega can be extremely small, making diff / vega blow up or become NaN. np.abs(diff) < tol evaluates False for NaN, so the loop simply runs to max_iter and, for a batch call, vol comes back with the bad strikes silently holding NaN mixed in with the good strikes' converged values — only a generic "max_iter reached" warning is logged, with no indication of which points failed or why.

Fix: Floor vega (e.g. np.maximum(np.abs(vega), eps)) or mask points below a vega threshold and fall back to implied_vol_brent for those, as the function's own docstring already suggests investigating.

#7 Binomial/trinomial tree risk-neutral probabilities are never validated to lie in [0,1] High
sdevpy/tree/trees.py · lines 71-78 (BinomialTree), 107-119 (TrinomialTree)

Why it's bad:

def calculate_probabilities(self, dt, drift, vol):
    stdev = vol * np.sqrt(dt)
    self.u = np.exp(stdev)
    self.d = 1.0 / self.u
    self.p = (np.exp(drift * dt) - self.d) / (self.u - self.d)

Same pattern in TrinomialTree.calculate_probabilities for pu/pd/pm. With few steps and a drift large relative to vol*sqrt(dt) (e.g. a large rate/dividend differential combined with a coarse step count), p can go negative or exceed 1 — arithmetically valid Python but financially meaningless, producing non-monotone or outright wrong option prices with no warning at all.

Fix: After computing the probabilities, assert/clip them into [0, 1] and raise a clear error (naming the offending step count/vol/drift combination) if they fall outside that range.

#8 GPT text generation never switches the model to evaluation mode — dropout stays active at inference High
sdevpy/llms/gpt_model.py · lines 17-34, 93-106  ·  sdevpy/llms/gpt/textgen.py · lines 77-109

Why it's bad: NextTokenGenerator.next() — the function every generation call goes through (respond_prompt → ChatGenerator.end_text → this) — only wraps the forward pass in torch.no_grad()::

def next(self, model, idx, context_size):
    idx_cond = idx[:, -context_size:]
    with torch.no_grad():
        logits = model(idx_cond)

torch.no_grad() disables gradient tracking but does not disable nn.Dropout. GptModel.load() never calls .eval() either, and since a freshly constructed nn.Module defaults to training=True, every call to respond_prompt/chat runs generation with dropout layers active. Worse, training.py's own train loop leaves the model in .train() mode after the final logging call (line 57), so post-training inference is affected too — generation is non-deterministic (beyond the seeded weights) and quality is degraded by unintended dropout noise on every response.

Fix: Call self.model.eval() in GptModel.load() (and again after train() completes), or at the top of ChatGenerator.end_text/NextTokenGenerator.next.

#10 Integer truncation in chart-grid sizing silently drops the last panel — or produces zero rows for a single-expiry surface Medium
sdevpy/volatility/impliedvol/optionsurface.py · lines 193-204

Why it's bad:

num_charts = expiries.shape[0]
num_cols = 2
num_rows = int(num_charts / num_cols)
...
fig, axs = plt.subplots(num_rows, num_cols, layout="constrained")
...
for i in range(num_rows):
    for j in range(num_cols):
        k = num_cols * i + j
        axs[i, j].plot(strikes[k], ref_disp[k], color='blue', label=ref_name)

int(num_charts / num_cols) truncates rather than rounds up. With 5 expiries, num_rows = int(5/2) = 2, so only indices k=0..3 are ever plotted — the 5th expiry's chart is silently never drawn, with no warning. With a single expiry (num_charts=1), num_rows = 0: plt.subplots(0, 2, ...) is called and the loop body never executes, producing no chart at all. This function (plot_transform_surface) is used from examples/stovol/stovoltrain.py and several StoVol training notebooks for diagnostic plots.

Fix:

num_rows = int(num_charts / num_cols)
num_rows = -(-num_charts // num_cols)  # ceiling division
